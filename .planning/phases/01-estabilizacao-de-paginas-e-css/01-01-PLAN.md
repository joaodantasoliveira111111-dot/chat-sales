# Phase 1 Plan 1: Estabilizacao de Paginas e CSS

<objective>
Corrigir os tres bugs da Fase 1: paginas criadas no dashboard devem continuar aparecendo imediatamente, `/p/[slug]` deve carregar a pagina publicada correta, e a UI publica/admin nao deve quebrar em telas pequenas por paddings ou larguras rigidas.
</objective>

<context>
Projeto Next.js 16.2.4 com App Router, React 19 e Supabase. Antes de editar rotas ou Server Components, leia a documentacao local em `node_modules/next/dist/docs/`, conforme `AGENTS.md`.

Arquivos ja identificados:
- `src/app/admin/pages/page.tsx`: Server Component que busca paginas, produtos, fluxos e temas.
- `src/app/admin/pages/PagesContent.tsx`: Client Component que cria, edita e remove registros em `public_pages`.
- `src/app/p/[slug]/page.tsx`: rota publica dinamica com `params: Promise<{ slug: string }>` e Supabase service-role client.
- `src/components/chat/PublicChatPage.tsx`: renderizador client-side do chat publico.
- `src/app/globals.css`: reset global, variaveis CSS e estilos base do admin/chat.
- `supabase/migrations/001_initial_schema.sql`: tabela `public_pages`, indice unico de slug e politicas RLS.
</context>

<must_haves>
- PAGE-01: Apos criar uma pagina em `/admin/pages`, o item aparece no topo da lista sem reload e persiste apos refresh.
- PAGE-01: Falhas reais do Supabase ficam visiveis no toast/log e nao sao mascaradas como sucesso.
- PAGE-02: `/p/[slug]` usa o slug correto, carrega apenas paginas `published`, inclui `product`, `flow`, `theme`, `flow_nodes` e `flow_edges` quando aplicavel, e retorna `notFound()` para slug inexistente/draft.
- PAGE-02: A URL publica exibida/copied no admin usa uma origem confiavel e nao aponta para dominio incorreto quando `NEXT_PUBLIC_APP_URL` estiver ausente ou mal configurado.
- UI-01: O layout publico funciona em mobile e desktop sem padding lateral excessivo, overflow horizontal ou elementos de chat/input cortados.
- O build e o lint continuam passando.
</must_haves>

<threat_model>
Riscos de seguranca relevantes:
- A rota publica usa `createAdminClient()` e contorna RLS. Mitigacao: manter filtros estritos por `slug` e `status = published`; nao expor paginas `draft` ou `archived`.
- O dashboard usa cliente de browser autenticado. Mitigacao: inserts/updates/deletes devem permanecer filtrados pelo usuario autenticado e nao aceitar `user_id` arbitrario de outro tenant.
- Slug globalmente unico pode vazar existencia de paginas de outro usuario via erro. Mitigacao: mostrar mensagem generica o bastante para o usuario final/admin e nao renderizar dados privados.
- `custom_css` e URLs de avatar/logo sao conteudo de usuario. Mitigacao desta fase: nao ampliar a superficie; se tocar renderizacao, manter escopo restrito e evitar interpolar HTML.
</threat_model>
